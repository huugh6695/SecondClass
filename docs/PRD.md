# PRD（精简版）· 第二课堂学时答疑服务台

> 版本 v1.0 ｜ 作者：本人 ｜ 状态：已上线
> 完整版 PRD 见项目早期文档；这里是给外部读者（面试官/合作者）看的浓缩版。

## 1. 背景与问题

第二课堂学时的答疑长期发生在微信群：

- 学生不知道自己的学时为什么没录上，只能在群里问，问题沉底就没人管
- 干事在几百条消息里翻找、私聊回复，同样的问题一天回答十几遍
- 处理过程没有记录，学期末无法回答「一共多少问题、多久解决、哪些最常见」

**问题的本质不是「没人回答」，而是「提问没有载体」**：群聊既不是队列，也不是数据库。

## 2. 目标与非目标

**目标（本学期）**

1. 让每一个学时疑问都有工单号、有负责人、有结果
2. 干事处理同样问题的时间成本下降
3. 管理者能按学部/时间段看到问题分布与解决时长

**非目标（明确不做）**

- 不做学时自动核算：学时认定规则由教务与学部掌握，系统不替代人工判断
- 不做小程序：审核与主体成本对校园内部工具不成立
- 不做即时聊天：微信已经在承担这个角色，再做一个只会两边都空

## 3. 用户与角色

| 角色 | 是谁 | 核心诉求 |
|---|---|---|
| 学生 | 需要核对学时的在校生 | 我的问题被看见、有回音 |
| 干事（STAFF） | 学部负责学时录入的同学/老师 | 高效处理、少重复回答 |
| 管理员（ADMIN） | 团委/学部管理方 | 数据可看、问题可追 |

## 4. 核心场景（按频率排序）

1. **学时缺失申诉**（最高频）：学生提交工单 + 证明材料 → 干事核查 → 回复或补录 → 学生确认
2. **规则咨询**：学生问「这个活动算不算学时」→ 命中常见问题直接给答案，未命中转工单
3. **重复问题聚合**：多个学生问同一件事 → 合并为一张主工单，避免干事回复十遍
4. **学期统计**：管理员按学部、时间、问题类型看分布与处理时长

## 5. 需求优先级

**P0（没有它系统不成立）**
- 工单提交（含附件）、派单/接单、回复、关闭
- 三类角色的鉴权与数据隔离
- 常见问题库（减少重复工单）

**P1（决定好不好用）**
- 工单状态流转记录（谁在什么时候改了什么）
- 学生确认态（避免「假解决」计入统计）
- 快捷回复模板（干事侧效率）

**P2（锦上添花，已实现但非核心）**
- 重复工单合并、操作日志、数据导出、敏感词过滤、公告、通知派发

## 6. 关键流程

```
学生：提交（标题/描述/附件）→ 等待 → 收到回复 → 确认 / 追问 → 关闭
干事：待办队列 → 接单 → 查附件与历史 → 回复（可套模板）→ 关闭 或 转交
管理员：总览 → 抽样核查 → 统计导出 → 维护 FAQ / 模板 / 敏感词
```

状态机：`待接单 → 处理中 → 已回复 → 已解决（学生确认）`，任一环节可被管理员强制关闭并记录操作日志。

## 8. 关键取舍（面试最常被问的三条）

1. **宁可多一个状态，也不少一个确认**：加了「已解决待确认」，统计口径变复杂，但避免把未解决算成已解决。
2. **附件故意放宽到 Office/PDF/压缩包**：与原始设计（仅图片）偏离，理由见 README「我做的几个判断」第 4 条。
3. **敏感词与黑名单放 Redis**：牺牲一点持久性，换高频路径上的延迟；两者都允许丢失重建。

## 9. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 工单无人接 | 系统空转、学生回到微信群 | 待办队列 + 学部值班表；上线首周人工盯 |
| 附件被滥用（大文件/违规内容） | 存储与合规风险 | 5MB 上限、扩展名白名单、敏感词过滤 |
| 学生不确认导致工单堆积 | 闭环率失真 | 定时提醒 + 管理员强制关闭留痕 |
| 单机部署 | 服务器故障即全站不可用 | 备份脚本 + 部署手册（见 `deploy/`） |
